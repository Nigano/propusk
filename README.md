# Propusk

Just-in-time privileged SSH access to Linux infrastructure with short-lived certificates.

[![CI](https://github.com/Nigano/propusk/actions/workflows/ci.yml/badge.svg)](https://github.com/Nigano/propusk/actions/workflows/ci.yml)
[![License: Apache 2.0](https://img.shields.io/badge/license-Apache%202.0-blue.svg)](LICENSE)

Propusk — выпускная квалификационная работа: система управления временным привилегированным доступом к Linux-инфраструктуре на основе краткоживущих SSH-сертификатов. Проект в разработке.

## Проблема

Администраторы заходят на серверы по постоянным SSH-ключам. Ключи годами лежат в `authorized_keys`, копируются между ноутбуками и не привязаны ни к задаче, ни к сроку. Украденный ключ даёт атакующему бессрочный доступ и свободу перемещаться по сети, а по журналам трудно понять, кто, когда и зачем заходил на сервер.

## Цель

Сократить окно возможностей атакующего: привилегированный доступ выдаётся только по заявке, на конкретные серверы, роль и время. Выдача доступа записывается в журнал с цепочкой хешей, а действия в сеансах уходят в центральное хранилище журналов вне сервера.

## Как это работает

1. Инженер входит в CLI `propusk` через Keycloak: OIDC, второй фактор TOTP, device flow.
2. Создаёт заявку: серверы, роль, срок и причина.
3. Политика решает, выдать доступ сразу или отправить заявку на согласование.
4. После одобрения OpenBao подписывает открытый ключ инженера: сертификат на 30 минут (не больше 8 часов), номер заявки в key ID, привязка к адресу через source-address.
5. Бастион открывает доступ в nftables на срок сертификата, а серверы доверяют только CA и не принимают постоянные ключи.
6. События пишутся в журнал с цепочкой хешей SHA-256. При отзыве обновляется список отзыва (KRL), активные сессии завершаются.

## Как проверяется

Одни и те же сценарии атак и замеры выполняются на четырёх конфигурациях одного стенда, развёрнутых из кода:

- B0 «как есть»: постоянные ключи, общая учётная запись;
- B1 «гигиена ключей»: личные ключи, раскладка и удаление через Ansible, вход только через бастион, центральные журналы;
- B2 «сертификаты без согласования»: сертификат на 8 часов сразу после входа, без заявки, сетевого окна и разрыва сеансов;
- P: Propusk.

Разница между соседними конфигурациями показывает вклад каждого механизма. Отдельно измеряется остаточное окно доступа: сколько времени нарушитель ещё может пользоваться украденным сертификатом или открытым сеансом.

## Ограничения

- Только доступ по SSH к серверам Linux. RDP, СУБД и сетевое оборудование в работу не входят.
- Сертификация не проводится, а компоненты (OpenBao, Keycloak, OpenSSH) не входят в единый реестр российского ПО, поэтому в нынешнем виде система не предназначена для ГИС и значимых объектов КИИ.
- Российские криптоалгоритмы не применяются.
- Запись сеансов ведётся на сервере, а не на шлюзе: нарушитель с правами root может остановить запись или доставку журналов. Записи, сделанные до остановки, уже лежат в центральном журнале, а цену этого ограничения измеряет эксперимент. Контроля команд на лету, как у шлюзовых PAM, нет.
- Направление развития: брокер обращается к удостоверяющему центру по API Vault, поэтому OpenBao можно заменить сертифицированным Deckhouse Stronghold, а Keycloak и ОС серверов сертифицированными отечественными решениями.

## Стек

OpenSSH certificates, OpenBao, Keycloak, nftables, Python (FastAPI, Typer), k3s, Helm, Argo CD, OpenTofu, Ansible, Incus, GitHub Actions.

## Структура

- `src/propusk/` — код сервиса и CLI
- `tests/` — тесты
- `docs/` — архитектурные решения (ADR), схемы, материалы ВКР
- `labs/` — заметки по учебным опытам
- `deploy/` — Docker Compose, Helm-чарт, манифесты Argo CD
- `infra/` — OpenTofu и Ansible для стенда
- `policies/` — политики выдачи доступа
- `attacks/` — сценарии атак для эксперимента
- `scripts/` — вспомогательные скрипты
